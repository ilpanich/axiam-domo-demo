<objective>
Complete the PKI story the tracer opened: assert every property of every certificate the listener table declares, export the root for human trust with a verifiable fingerprint, and make it structurally hard to leak the root key.

Purpose: the tracer proved *one* chain works. PKI-04 is about *every* chain being correct — SANs, lifetimes, extensions, issuer — and PKI-05/PKI-06 are about the two things a demo actually fails on: a browser that shows a warning, and a private key that ends up in a commit.

Output: `just verify-pki`, `just export-trust`, `just pki-rotate-root`, a pre-commit secrets guard, `docs/trust.md`, and `docs/dogfooding-findings.md`.

This plan also carries the phase's dogfooding log (D-32, D-33). It sits here rather than with the tracer because it has no dependency on the tracer chain and every other task in this plan is the same shape — a written artifact plus the check that keeps it honest.

**Reversibility:** everything here is `reversible` — verification scripts, an export recipe and a documentation file can be reshaped freely. `just pki-rotate-root` is the one **costly** action it exposes: running it invalidates the trust every client machine has already installed, which is why it is a separate, explicitly named recipe and never part of `just demo-reset` (D-10).
</objective>

Do not rely on `.gitignore` alone — an explicit `git add -f` bypasses it, which is exactly the accident this catches.

    Second, ignore-integrity: `git check-ignore -q .secrets/pki/root.key` must succeed, and `git ls-files .secrets dist` must print nothing. If either fails the ignore rules have been weakened.

    Third, build-context integrity: assert `.dockerignore` lists both `.secrets` and `dist`, and that no Dockerfile under `deploy/docker/` copies from a path that would reach them. Additionally, for any locally built image that exists, stream its layers through `docker save` and a tar extraction and count occurrences of the standard PEM private-key header, requiring a count of zero; skip this third sub-check with a printed `→ skipped (image not built)` when the image is absent, so the guard is usable before the first build.

    Do not change any `.secrets/` file mode to make a container able to read a file — the `tls-init` copy service from plan 01-01 exists for that, and loosening modes here is the failure this guard is meant to prevent.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| `.secrets/` → git index | The single most likely way the root key escapes. Crossed by `git add`, deliberately or otherwise. |
| `.secrets/` → Docker build context | Crossed silently by a broad `COPY .`; the result is a key baked into a distributable layer. |
| `dist/trust/` → the operator's OS and browser trust stores | A human action that grants this root authority over every TLS connection that machine makes. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02-01 | Information disclosure | `.secrets/pki/root.key` reaching a commit | critical | mitigate | Three independent layers: `.gitignore`, a pre-commit hook that refuses staged `.secrets/` paths even when force-added, and an ignore-integrity assertion that fails if the ignore rule is weakened. |
| T-02-02 | Information disclosure | root key baked into an image layer | critical | mitigate | `.dockerignore` assertion plus a `docker save` scan of every locally built image requiring a count of zero for key material. |
| T-02-03 | Spoofing | a wrong or substituted root installed on the operator's machine | high | mitigate | The fingerprint is published in three places — `dist/trust/domo-root.sha256`, the printed `export-trust` output, and the landing page — and `docs/trust.md` instructs the reader to compare before trusting. |
| T-02-04 | Elevation of privilege | a demo root left permanently trusted on a reviewer's machine | medium | mitigate | `docs/trust.md` carries a removal section per target, so trust is reversible by the person who granted it. The root is LAN-only and never served over HTTP, limiting its reach. |
| T-02-05 | Tampering | a certificate with a weakened or missing extension passing unnoticed | high | mitigate | `just verify-pki` asserts basic constraints, key usage, extended key usage, SAN presence and non-emptiness, lifetime bound and chain verification for every row of the listener table, and fails on the first violation naming the listener. |
| T-02-06 | Repudiation | a rotated root leaving machines silently trusting a dead anchor | low | accept | `just pki-rotate-root` prints a loud warning and `docs/trust.md` states every listed machine must repeat its step. Accepted: a LAN demo has no revocation infrastructure and none is in scope. |
| T-02-07 | Repudiation | a hand-rolled AXIAM workaround with no recorded finding | medium | mitigate | The findings log defines every `DF-` identifier the code cites, and this plan asserts the resolution for every citation plan 01-01 already wrote. The recurring gate that keeps the two in step as later phases add workarounds is built in plan 01-07 Task 3 and runs inside `just verify` from then on. Without it the dogfooding deliverable degrades into a set of undocumented workarounds that look like ordinary code. |
| T-02-SC | Tampering | package installs | low | accept | This plan installs nothing — it uses `openssl`, `git` and `just`, all already present and verified in RESEARCH § Environment Availability. No package-legitimacy checkpoint is required. |
