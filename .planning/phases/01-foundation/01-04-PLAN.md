<objective>
Establish AXIAM's authorization model for the whole project: a checked-in role and permission catalog applied identically to both tenants, a per-tenant admin principal that makes tenant-scoped work possible at all, one signing CA and one service-account credential set per tenant, each tenant's portfolio root, and the helper that creates a resource together with its structural groups.

Purpose: every later phase resolves permissions, groups and resources through the names decided here. AUTHZ-01 and AUTHZ-02 are the demo's actual subject matter — the four key moments are all statements about this model — and the names are costly to change once three phases read them.

Output: `authz/catalog.toml`, the `tenant-admin`, `catalog`, `tree` and `service-certs` stages of `domo-bootstrap`, and `just authz-verify`.

**Reversibility:** the catalog contents (D-16) and the naming scheme (D-17) are **costly** — Phase 2's Management Platform, Phase 3's Twin and every smoke assertion resolve through these exact strings, so renaming one later breaks three phases at once. The one-service-account-per-(service, tenant) model (D-20) is likewise **costly**: Phase 2 and Phase 3 each hold one credential set per tenant and route by tenant. The stage decomposition and the helper's internals are **reversible**. No `checkpoint:decision` is inserted: all three costly decisions were locked by the user in CONTEXT.md, and re-opening them would contradict the phase context.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| organization scope ↔ tenant scope | The most consequential boundary in the project. An organization principal acting inside a tenant is what the acting-tenant header exists for, and what the SDK cannot express. |
| tenant `lakeside` ↔ tenant `summit` | The isolation the demo exists to show. Enforced by separate admin principals, separate signing CAs and separate service credentials. |
| `.secrets/axiam/` → the filesystem | Tenant-admin passwords and service private keys live here at mode 0600. |
| `domo-bootstrap` → AXIAM REST | Privileged: creates users, assigns super-admin roles, signs certificates. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-04-01 | Tampering | tenant-scoped writes landing in the reserved organization tenant | high | mitigate | The organization client and the tenant client are distinct types, so the mistake is a compile error rather than a silent write. `just authz-verify` independently asserts every created object's tenant id. This failure is silent in AXIAM — no error is returned — which is why two layers guard it. |
| T-04-02 | Elevation of privilege | a certificate for one tenant issued under another tenant's signing CA | high | mitigate | Every signing call passes the acting tenant's own CA, and verification asserts both that each certificate chains through its own CA and that it fails under the other tenant's. AXIAM checks the issuing CA belongs to the organization but apparently not that it belongs to the acting tenant, so the caller carries this. |
| T-04-03 | Elevation of privilege | the organization super-admin credential leaking into a service | high | mitigate | The super-admin is used only by `domo-bootstrap` for organization-scoped work; every service gets a per-tenant credential instead. Prohibited by an explicit prohibition and asserted by the absence of that credential from any service's environment. |
| T-04-04 | Information disclosure | tenant-admin passwords or service private keys at loose permissions | high | mitigate | Written under a restrictive umask at mode 0600 into `.secrets/`, which is git-ignored and docker-ignored; verification fails on any file looser than 0600. The tenant CA's own key is returned once, is a redacting sensitive type, and is deliberately discarded. |
| T-04-05 | Elevation of privilege | a deny rule created above an apartment or device node | medium | mitigate | Prohibited explicitly; the catalog contains no deny concept and the tree helper creates none. AUTHZ-08 makes this a seeded check in Phase 2. |
| T-04-06 | Tampering | duplicate sibling resources making an authorization decision ambiguous | medium | mitigate | Every create resolves by name under the parent first, using a server-side search rather than client-side filtering of one page, and verification asserts exactly one child per name. No uniqueness index on resource names was found, so this is the only guard. |
| T-04-07 | Spoofing | a group name collision granting unintended scope | medium | mitigate | Group names are generated by one pure, unit-tested function; slugs are validated to lowercase letters, digits and hyphens, rejecting the dot and colon that would break topic segmentation and broker virtual-host parsing. |
| T-04-08 | Repudiation | a hand-rolled call with no corresponding finding entry | low | mitigate | Every public function in the hand-rolled module carries a doc comment naming its finding identifier, and plan 01-01's audit gate fails when a cited identifier has no entry. |
| T-04-SC | Tampering | cargo installs | low | accept | This plan adds no new dependency; it uses the workspace dependency set already resolved through plan 01-01's blocking package-legitimacy checkpoint. |
