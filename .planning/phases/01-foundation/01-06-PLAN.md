<objective>
Build one real branch of the resource tree in one tenant, with its structural groups, and prove against live AXIAM and a live broker that the authorization model and the device identity chain both behave — positively and, more importantly, negatively.

Purpose: plans 01-04 and 01-05 proved their pieces in isolation. This is where the group-per-(role, resource) pattern meets a real access check, and where the four-hop device identity chain meets a real TLS handshake, a real broker and a real token. The negative cases are the point: a demo whose denials do not actually deny has no story to tell.

Output: `just smoke`, re-runnable after every reset, asserting a matrix of expected outcomes and exiting non-zero on any surprise.

**Reversibility:** all `reversible`. The smoke branch is created and destroyed by reset, the matrix is a test harness, and the probe's case list can be extended freely. The one **costly** dependency is the reserved fixture prefix, which Phase 2's seed must continue to avoid.
</objective>

    Turn the probe from a single happy path into a matrix harness. `cases.rs` declares each case as data — a name, how to build the identity and credentials, and the expected outcome — and `matrix.rs` runs them all, reports one line per case, and exits non-zero if any case's observed outcome differs from its expectation. Expected outcomes must be specific: not merely "fails", but which layer refuses and with what signal, so that a case failing for a new reason is visible rather than absorbed.

    The cases, each with its own expected outcome:
    - Positive. The probe's own certificate and its own token: connect succeeds, a publish to its own topic succeeds, a subscribe to its own namespace succeeds, and the published message comes back. Also assert the session shows up on the `domo` virtual host under the probe's own identifier when the broker's management interface is queried.
    - Mismatched certificate. The probe's valid token presented with a second device's certificate: refused. Expected signal is the broker's client-identifier rejection, because the client identifier must equal the certificate subject and the token subject must equal the user name — state which of the two is expected to fire first.
    - Malformed token. A structurally invalid string as the password: refused at the authorization decision, not at the handshake.
    - Bad signature. A well-formed token signed by a key the key set does not contain: refused at the authorization decision.
    - Wrong tenant. A token issued for the other tenant presented with this tenant's certificate: refused, and note that this is the case that would pass if the Twin's per-tenant verifier assertion were removed.
    - No client certificate. Connect with no identity at all: refused at the TLS handshake, before any authorization decision is reached — assert the failure is a handshake failure rather than a connect-refused, since the difference tells you whether the broker's peer-certificate requirement is actually on.
    - Other tenant's CA. A certificate issued under the other tenant's signing CA presented with this tenant's credentials: refused.
    - Namespace escape. A publish one segment outside the probe's own namespace: refused. A publish into the other tenant's namespace: refused. Include the adjacent-name case — a namespace whose prefix extends the probe's own — because a prefix comparison in the Twin would pass it.
    - Empty certificate binding. A service account with no bound certificate attempting a device login: expect 401, which is what "authenticates as nobody" means concretely.
    - Cross-tenant certificate issuance. Attempt to have a certificate signed under the other tenant's signing CA. Record the outcome either way: a refusal confirms AXIAM binds the issuing CA to the acting tenant; an acceptance is a confirmed finding, must be written into the findings log, and must fail the matrix so the result is not silently absorbed.
