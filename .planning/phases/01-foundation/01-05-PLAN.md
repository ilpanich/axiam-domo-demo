<objective>
Harden the Device Twin's RabbitMQ authorization backend from the tracer's working happy path into the complete four-endpoint contract, with the decision logic as pure functions and a unit suite that exercises every denial reason without needing a broker, a device, or a network.

Purpose: this is where MQTT-02 actually lives. The broker enforces one hop of the identity chain at the TLS handshake; the other two hops are code in this service, and they are the difference between "a stolen token is useless" and "a stolen token works from any machine". Every one of those hops needs a test that fails when the check is removed.

Output: `services/device-twin` with strict request parsing, a pure decision core, a per-tenant verifier registry, and three test files covering the whole denial surface.

**Reversibility:** all `reversible`. The endpoint paths and response shapes are dictated by the broker's contract rather than chosen, the decision functions are pure and replaceable, and the only externally visible commitment is the topic scheme in `domo-common`, which is shared with the probe and Phase 4's simulators and is therefore **costly** rather than one-way.
</objective>

  <action>
    Restructure `services/device-twin/src/rmq.rs` into a thin handler layer over two new modules, preserving the behaviour the tracer proved.

    `forms.rs` holds one strict request struct per endpoint, matching the parameter lists the broker actually sends: the user endpoint receives a user name, a password, a virtual host and a client identifier; the virtual-host endpoint receives a user name, a virtual host, an address and tags; the resource and topic endpoints receive a user name, a virtual host, a resource kind, a name, a permission and tags, with the topic endpoint additionally receiving a routing key and a variable map covering user name, virtual host and client identifier. Use the framework's typed form extractor with strict structs — reject unknown fields and missing required fields rather than defaulting — and make the client identifier explicitly optional at the type level, because a request without one must decide deny rather than fail to parse.

    `decide.rs` holds the decisions as pure functions taking already-parsed inputs and an injected verification outcome, returning a decision enum carrying an optional reason. Purity is the point: these functions are what the tests exercise, and they must be callable with no server, no network and no clock beyond an injected instant.

    Implement the user decision in the order that costs least first: virtual host must be `domo`; the user name must parse as a service-account identifier; the client identifier must be present and exactly equal to the user name with the common-name marker prefixed; only then is the token verified. That ordering matters because it means a malformed or hostile connect is rejected before any key-set work.

    Implement the virtual-host decision as a pure cache lookup: present, not expired, and naming `domo`. Deny on every other outcome including a miss — these endpoints receive no token and have no other evidence, so failing open here would grant every subsequent operation for free.

    Every handler returns HTTP 200 with a plain-text body of exactly `allow`, or `deny`, or `deny` followed by a reason. Never return a 4xx or 5xx for an ordinary decision: the broker reads any other status as an error, not a denial, which silently changes failure semantics. Build reason strings from the decision enum only, so no reason can ever interpolate a password or a token.

    Add a `wiremock` dev-dependency (0.6, the same version the SDK itself uses) to `services/device-twin/Cargo.toml` for the later tasks, and create `just/twin.just` with `twin-test` and `twin-run`.

Plan 01-04 compiles into the same `target/` in this wave under D-29's single workspace, so the space this task leaves behind is space that plan does not have; do not start here if the 25 GB concurrency bound in the precondition is unmet.

    Selecting which tenant's verifier to try is the one genuinely subtle part. Read the unverified tenant claim from the token to pick a candidate verifier, then let that verifier perform the real verification including its own tenant assertion — so the unverified read is only a routing hint and never a trust decision. If the claimed tenant has no registered verifier, deny immediately. Never try every verifier in turn: that would make the tenant assertion meaningless, because a token would succeed as soon as any tenant accepted it.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| `rabbitmq` → `device-twin:8443` | Every CONNECT, subscribe and publish decision crosses here. The caller is the broker, which presents no AXIAM session. |
| device-supplied token → verified claims | The token arrives as an MQTT password from an untrusted device and is the only assertion of identity the Twin ever sees. |
| tenant `lakeside` ↔ tenant `summit` | Separated here by which verifier a token is routed to, and by the tenant segment of the topic namespace. |
| in-memory cache → the three token-less endpoints | The only evidence available to the virtual-host, resource and topic decisions. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-05-01 | Spoofing | a stolen token replayed with an unrelated certificate | high | mitigate | Two of the three identity hops live here: the client identifier must equal the user name with the common-name marker prefixed, and the token subject must equal the user name. The broker holds the third at the handshake. Each hop has a test that fails when the check is deleted. |
| T-05-02 | Elevation of privilege | a token valid for one tenant accepted for another | high | mitigate | One verifier per tenant, each asserting its own tenant claim; the unverified claim is used only to route to a candidate and never as a trust decision; verifiers are never tried in turn. The key-set endpoint is organization-wide, so without this a valid signature alone would suffice. |
| T-05-03 | Elevation of privilege | a device reaching another device's queues or topics | high | mitigate | The resource decision allows only the shared exchange and the names derived from the connecting client identifier; the topic decision uses a separator-aware namespace predicate rather than a prefix comparison, with the adjacent-name case asserted explicitly. |
| T-05-04 | Elevation of privilege | reaching AXIAM's own virtual host through the device path | high | mitigate | Every endpoint denies any virtual host other than `domo`, checked first and before any token work. |
| T-05-05 | Spoofing | fail-open on a cache miss, a parse failure or an internal error | high | mitigate | The three token-less endpoints deny on a miss by construction, and every uncertain path in the pure decision functions resolves to deny. A Twin restart therefore forces reconnection rather than silently granting. |
| T-05-06 | Tampering | a non-2xx response being read by the broker as an error rather than a denial | medium | mitigate | Every handler returns HTTP 200 with a plain-text body for both outcomes, asserted per endpoint. Prohibited explicitly, because the failure is invisible in normal operation. |
| T-05-07 | Information disclosure | the device token appearing in a log record or a denial reason | high | mitigate | Reason strings are built from a decision enum and can never interpolate a credential; a test captures log output during a denial and asserts the password value is absent. The broker-side half — keeping the token out of the request URL — is handled by the POST method in plan 01-01's broker configuration. |
| T-05-08 | Denial of service | an unbounded cache or unbounded verification work from hostile connects | medium | mitigate | The cheapest checks run first, so a malformed user name or client identifier is rejected before any key-set work; cache entries carry the token's own expiry and are evicted on it. Full load behaviour at 114 devices is Phase 3's concern. |
| T-05-09 | Tampering | hand-rolled verification drifting from the SDK's guarantees | medium | mitigate | Prohibited. The SDK's verifier pins the algorithm before key lookup and enforces tenant, audience, expiry and skew together; a replacement would need all four right at once. |
| T-05-SC | Tampering | cargo installs | low | mitigate | One new dev-dependency, `wiremock` 0.6, already used by the SDK itself and audited as approved with multi-year history in the package-legitimacy audit. No production dependency is added. |
