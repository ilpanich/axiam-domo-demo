<objective>
Prove the single trust anchor end to end, in one thin vertical slice: an offline-generated organization root that AXIAM imports (BYOK), one tenant with one AXIAM-issued signing CA, one device service account whose locally-generated CSR is signed and bound by that CA, an mTLS device login that returns a JWT, and an MQTT CONNECT on the `domo` vhost that the Device Twin's RabbitMQ HTTP auth backend accepts.

Purpose: this is the architectural bet of the whole project. If the cert→client_id→username→`sub` chain does not hold against a real RabbitMQ and a real AXIAM, every later phase is built on sand. Proving it now costs one commit; discovering it in Phase 4 costs the demo.

Output: a working `just tracer` that goes from an empty machine to an accepted MQTT CONNECT, plus the repository skeleton (Cargo workspace, compose stack, broker config, offline PKI script) that plans 01-02…01-07 expand.

**Reversibility:** no decision implemented here is `one-way`. The root generation + BYOK import is **costly** — `just pki-rotate-root` (plan 01-02) exists, but rotating invalidates every machine that has already trusted the root. The repo layout (D-28), the Cargo workspace shape (D-29) and the one-service-account-per-(service, tenant) model (D-20) are **costly**: paths and credential shapes are baked into the justfile, compose and every later phase. The compose file (D-02), the broker fragment (D-26) and the tracer's stage set are **reversible**. No `checkpoint:decision` is inserted, because every costly decision here was already locked by the user in CONTEXT.md and re-opening it would contradict the phase context.
</objective>

    **`tools/domo-bootstrap`.** A clap-derive CLI with one subcommand per stage; this task implements `org-bootstrap`, `tenants`, `pki`, `device-identity` and `broker`. Every stage is idempotent by probe, not by marker — resolve by natural key (tenant by slug, service account by name), create only if absent, and treat `.secrets/state/<stage>.done` as a skip hint only. `org-bootstrap`: the setup token is scraped by `just` from the full `docker compose logs --no-color axiam-server` history (not `--since`) with the JSON key `setup_token`, persisted to `.secrets/state/setup-token` at mode 0600 the moment it is seen, and passed in; the stage calls the hand-rolled `/admin/bootstrap` with `organization_name`, `organization_slug`, `email`, `username`, `password`, `setup_token` — omit the deprecated tenant fields — and accepts `201` and `409`, while `403` means the gate is already consumed and the stage falls through to probing `POST /api/v1/auth/login` with the saved super-admin credentials; if neither the token nor a working login exists it exits non-zero with `reset required: run 'just demo-reset'` (D-12, P-3, DF-019). Super-admin credentials are persisted to `.secrets/axiam/super-admin.json`. `tenants`: creates Lakeside Residences / `lakeside` only in this task. `pki`: imports the root with `ImportCaCertificateRequest { private_key_pem: Some(Sensitive(..)), public_cert_pem }`, sets `SetMtlsTrustAnchor { enabled: true }` on it, then `generate_signing_ca(tenant_id, CreateIntermediateCaRequest { key_algorithm: KeyAlgorithm::Ed25519, parent_ca_id: <root id>, subject, validity_days })` — the returned CA private key is `Sensitive` and returned once; discard it deliberately, AXIAM keeps custody, and never debug-format a struct that may contain one. `device-identity`: creates the probe's service account, takes a CSR on stdin or a path, calls `certificates().sign_csr(SignCertificateCsrRequest { cert_type: CertificateType::Device, csr_pem, issuer_ca_id: <the acting tenant's CA>, .. })` and then the mandatory `service_accounts().bind_certificate(..)` — without the bind the certificate is valid TLS material that authenticates as nobody. Because the SDK never sends the acting-tenant header, this stage runs on a **tenant-scoped** client: `domo-bootstrap` first provisions a tenant-admin user with four hand-rolled calls carrying `X-Axiam-Tenant` (create user, activate to `Active`, find the tenant's `super-admin` role, assign it) and logs in a second `AxiamClient` as that user (D-37, P-1).     **`services/device-twin`.** An Actix app bound with `bind_rustls_0_23` on `:8443` (TLS 1.3 only, D-07) exposing `GET /healthz` and `POST /rmq/{user,vhost,resource,topic}`. Each handler takes `actix_web::web::Form<T>` over a strict struct and returns `text/plain` with exactly `allow` or `deny` or `deny <reason>` — any other status is an error to the broker. `/rmq/user` denies unless the vhost is `domo`, the `client_id` equals `"CN=" + username`, the JWT verifies, and its `sub` equals `username`; verification uses `axiam_sdk::token::JwksVerifier` built per tenant with `expect_tenant_id` and `expect_audience("axiam:m2m")` — the JWKS endpoint is organization-wide, so without `expect_tenant_id` the verifier proves only "some tenant in this org". On success cache `username → {tenant_id, tenant_slug, exp}` in memory; `/rmq/vhost`, `/rmq/resource` and `/rmq/topic` read that cache and deny on a miss. `/rmq/resource` allows the `amq.topic` exchange and the connecting device's own `mqtt-subscription-<client_id>qos0`, `mqtt-subscription-<client_id>qos1` and `mqtt-will-<client_id>` names. `/rmq/topic` allows a routing key only under `domo.<tenant_slug>.<sa-uuid>.`. Keep the decision logic in a pure, separately callable function so plan 01-05 can unit-test it without a server. Never log a request body, a password field, or a token.

    **`tools/domo-probe`.** Generates an Ed25519 keypair and a PKCS#10 CSR with subject `CN=<device service-account UUID>` using `rcgen` — the key never leaves the probe (D-23, DEV-05). Hands the CSR to `domo-bootstrap device-identity`, receives the signed leaf, then hand-rolls `POST /api/v1/auth/device` over mTLS with a `reqwest` identity built from leaf + tenant CA + key, expecting `{ access_token, token_type: "Bearer", expires_in }`; the Rust SDK has no device-login method and its `device_login` is the unrelated OAuth Device Authorization Grant, so do not reach for it (C-6, DF-009). Then connects with `rumqttc` over rustls: `client_id = "CN=<sa-uuid>"`, `username = <sa-uuid>`, `password = <the access token>`, port 8883. Publishes to `domo/lakeside/<sa-uuid>/reported` and subscribes to `domo/lakeside/<sa-uuid>/#`, asserting the round trip. Exit non-zero with the broker's own reason on any failure. Do not print the token.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| operator host → container network | The root private key crosses here exactly once, as a BYOK import payload over TLS. `.secrets/` is host-owned, 0600, mounted read-only via the `tls-init` copy. |
| LAN → `axiam-server:8090` | Untrusted device and browser traffic. Native mTLS with `client_auth = optional`, so one listener serves both device login and ordinary TLS. |

| `rabbitmq` → `device-twin:8443` | Internal only. Authorization decisions for every CONNECT, publish and subscribe. |
| `domo-bootstrap` → `axiam-server` | Privileged: super-admin and tenant-admin sessions, CA import, certificate signing. |
| `axiam-server` → `rabbitmq:5671` | AXIAM's own AMQPS link, which broker-wide peer verification now forces to present a client cert. |
