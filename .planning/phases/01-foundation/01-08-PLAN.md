<objective>
Close UAT gap **G-01-3**. `just verify` must be green on the live stack, and SC2 verify-pki must actually assert the RabbitMQ 8883 row on every run.

Root cause (binding; from `.planning/debug/verify-pki-rabbitmq-flake.md`): `scripts/verify-pki.sh` `verify_live()` decides both TLS reachability (~L344) and chain verification (~L367-369) from `openssl s_client … </dev/null`'s **exit status**, with no client certificate. RabbitMQ's 8883 listener requires one (D-24, D-26: `verify_peer`, `fail_if_no_peer_cert`, TLS 1.3 only). Under TLS 1.3 the broker rejects the empty client Certificate with a fatal `certificate_required` alert (116) only after the client has finished its handshake. s_client therefore exits 0 or 1 depending on whether it reads stdin EOF or the alert first. That is a scheduling race: about 1-4% of probes lose it idle, about 90% under CPU load. The chain itself always verifies. The same race in the reachability probe makes verify-pki **silently skip** the row and exit 0. `just verify`'s `group()` then hides the skip, so the phase gate shows green for a row it never checked.

Fix, in three vertical slices:
1. **Tracer.** Judge the handshake from markers that only a completed, verified TLS 1.3 client handshake prints, never from the exit status. Prove it on the rabbitmq row under bounded CPU contention, with the guard shown RED on the old code first.
2. **Never skip a published row silently.** While the stack is up, a published server row that cannot be asserted fails. Remove the optional-tool path that could skip every row.
3. **Surface skips in `just verify`.** Leave the fast gate green on the live stack.

Purpose: the phase gate must mean what it says. A gate that flakes red trains people to re-run it until it passes, and a gate that silently skips a row reports assurance it did not produce.

Output: `scripts/verify-pki.sh` (verdict helpers, strict live semantics, `--live-only`, source guard), `just/pki.just` (`verify-pki-stress`), `just/verify.just` (skip surfacing).
</objective>

## Planner discovery: what s_client actually prints (OpenSSL 3.6.4, live stack, 2026-09-29)

Every row was observed directly against the running stack. Together they rule out the obvious single-line verdicts:

| Probe | exit | `SSL_connect:SSLv3/TLS write finished` (from `-state`) | `New, TLSv1.3, Cipher is …` | `Verify return code: 0 (ok)` | `Protocol: TLSv1.3` |
|---|---|---|---|---|---|
| rabbitmq 8883, root CA, stdin EOF first | 0 | yes | yes | yes | yes |
| rabbitmq 8883, root CA, alert read first (forced with `sleep 2 \|`) | 1 | yes | yes | yes | yes |
| rabbitmq 8883, a throwaway CA (chain does not anchor) | 1 | **no** | **yes** | no (19) | yes |
| 127.0.0.1:15673, plain HTTP, no TLS at all | 1 | no | no (`(NONE)`) | **yes** | **yes** |
| caddy 443 / axiam-server 8090, root CA | 0 | yes | yes | yes | yes |

Consequences:
- `Protocol: TLSv1.3` and `Verify return code: 0 (ok)` both appear for a port that does not speak TLS at all, so neither one alone is evidence.
- `New, TLSv1.3, Cipher is …` appears when the chain was refused, because the cipher comes from ServerHello.
- `SSL_connect:SSLv3/TLS write finished` is printed only when the client has written its own Finished. That requires the server certificate to have passed `-verify_return_error`, the server's CertificateVerify to have proved key possession, and the server's Finished to have been verified.
- The verified verdict therefore requires **all three** of: that `write finished` line (exact), the `New, TLSv1.3, Cipher is ` line (prefix), and `Verify return code: 0 (ok)` (exact). Do not use `Protocol:` or `Verification: OK`: the first is meaningless (see above), and the second varies across OpenSSL versions. The three chosen markers are stable from OpenSSL 1.1.1 to 3.6, which matters because the Pi runs a Debian-based OpenSSL 3.0.
- For reachability (does this port speak TLS at all), the exact `-state` line `SSL_connect:SSLv3/TLS read server certificate` was present on 8883, 443 and 8090 and absent on 15673. Match it as a whole line: `…read server certificate request` is a different line.
- `-state` writes to stderr and the summary goes to stdout, so capture both streams (`2>&1`).
- Bounded load test at planning time: 24 busy loops (2 × nproc on 12 cores) under `timeout`, 40 probes of rabbitmq 8883. The exit-status verdict failed **36/40**. The three-marker verdict failed **0/40**. Every hog was reaped afterwards.
