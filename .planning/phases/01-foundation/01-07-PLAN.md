    Build the interruption hook the resume path has to be testable through, in the same module that owns the stage sequence. Read the `DOMO_FAIL_AT` environment variable once at start; when its value names a stage, the runner aborts at the entry of that stage — before the stage does any work and before it writes `.secrets/state/<that stage>` — exiting non-zero with the ordinary stage-failure output so the abort is indistinguishable from a real failure at that point. When the variable is unset or names no stage, the runner behaves exactly as it does in production; the hook adds no branch inside any stage's own logic. Without it there is no way to produce a half-finished run on demand, and "an interrupted run resumes at the stage that failed" (D-34, PLAT-05) stays an untested claim.

    That variable has a container boundary to cross, and crossing it is this task's job rather than the operator's. `domo-bootstrap` is a compose one-shot invoked through `docker compose run --rm` (plan 01-01), so a value set in the operator's shell reaches `just` and stops there unless the stage runner carries it further: the invocation of that one-shot forwards `DOMO_FAIL_AT` into the container whenever the calling environment has it set. Forwarding an empty value is harmless, because the hook already treats a value naming no stage as unset. Apply the same abort in the task runner for the stages it owns itself — preflight, AXIAM up and platform up — so that every name in D-34's sequence behaves identically no matter which side of the boundary runs it. Skip the forwarding and the resume gate below fails at its very first step, with an executor left to guess why a variable it set was ignored.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| operator host → Docker daemon | Volume removal and image building. The blast radius includes the sibling checkout's development data. |
| `.secrets/demo-card.txt` → the operator's screen | Contains the super-admin login; printed to a terminal and written to disk. |
| build machine → the Raspberry Pi | Images cross the architecture boundary; a wrong-architecture image fails at run time on the second machine, not at build time on the first. |
| stage markers → stage execution | Markers decide what is skipped. A marker that is trusted as truth is a correctness boundary, not a performance one. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-07-01 | Denial of service | reset destroying data outside this project | high | mitigate | Volumes are removed one by one by explicit name and pruning is prohibited and asserted absent from the orchestration. The sibling checkout's volumes hold development data that is not ours to destroy. |
| T-07-02 | Tampering | the organization root removed by reset | high | mitigate | Reset clears every marker except the root's, and a verification step compares the root's fingerprint across a reset. Rotation lives in a separate recipe that never appears in an automated path, because rotating silently invalidates the trust every client machine has installed. |
| T-07-03 | Tampering | a stage skipped on a marker with no work behind it | high | mitigate | Markers are a skip hint only; every stage re-probes its real state, and each marker is self-describing so a human can see what actually happened. The sibling project learned this the hard way: a run that died mid-request leaves a zero-length marker that skips the work forever. |
| T-07-04 | Information disclosure | the super-admin login on a demo card | medium | mitigate | Written at owner-only mode into the git-ignored and docker-ignored secrets directory, asserted by a mode check. Printing it to the operator's own terminal is intended; it is the presenter's credential. |
| T-07-05 | Information disclosure | the one-time bootstrap token in container logs | medium | mitigate | Scraped once, persisted at owner-only mode, and single-use. Inherited from plan 01-01; the resume path treats an already-consumed token as a normal outcome rather than an error. |
| T-07-06 | Denial of service | a full disk producing failures that look like compiler bugs | high | mitigate | Preflight refuses below roughly 8 GB, builds refuse to run concurrently below 25 GB, free space is asserted after each image build, and build outputs are cleaned. This has already happened on this machine once. |
| T-07-07 | Spoofing | an image built for the wrong architecture failing only on the second machine | medium | mitigate | Every image the compose file references is asserted against its manifest for the target architecture, at build time on the first machine rather than at run time on the second. |
| T-07-08 | Repudiation | a hand-rolled workaround with no recorded finding | medium | mitigate | The findings audit runs inside the fast gate: every cited identifier must resolve to an entry, and a call with no citation fails. Running it every time is what keeps the log honest as later phases add workarounds. |
| T-07-09 | Tampering | the two reference machines silently diverging | medium | mitigate | Exactly one compose file is asserted to exist; the machines differ only in their generated environment file. A per-host override is prohibited, because it is the point at which the Pi run stops proving anything about the laptop run. |
| T-07-SC | Tampering | image and toolchain installs | medium | mitigate | Every base image is pinned and, where the sibling project does so, digest-pinned; nothing is built from a sibling checkout. The cross toolchain is added inside the builder image rather than to the host, so a failed experiment is thrown away with the layer. No new package-manager dependency enters the runtime images. |
