# Stack Research

**Domain:** Multi-tenant IoT home-automation demo, fronted by the AXIAM IAM server, on Docker Compose across amd64 (ArchLinux laptop) and arm64 (Raspberry Pi 5)
**Researched:** 2026-09-19
**Confidence:** HIGH for anything pinned by an AXIAM SDK `pom.xml`/`Cargo.toml`/`CMakeLists.txt` or by AXIAM's own `docker/*.yml` (read directly from the repos). MEDIUM for versions confirmed by web search against vendor docs/release notes dated 2026. LOW is called out explicitly where it occurs (none load-bearing below).

## Correction to the milestone brief before anything else

The milestone context states "Java 21, Spring Boot 3.x" for the Management Platform. **That is out of date and should not go into the roadmap as written.** `/home/emanuele/git/priv/axiam-java-sdk/pom.xml` pins its optional Spring integration to `spring-boot-starter-security:4.1.1` and `spring-webmvc:7.0.9` (Spring Framework 7 / Spring Security 7 — the Spring Boot **4.x** line), and the SDK's own `examples/spring-boot-app/pom.xml` says so explicitly in a comment: *"D-15/D-16: Spring Boot 4.x/Security 7.x, jakarta.* namespace. Pinned to the same 4.1.0 line as the SDK pom's spring-boot-starter-security."* Spring Boot 4.0 shipped 2025-11-20 and 4.1 shipped 2026-06-10, so by the time this milestone is built, 3.x is not just "an older option" — it is the line the SDK was never validated against. Building the Management Platform on Spring Boot 3.x would mean loading `AxiamAuthenticationFilter`/`AxiamAuthorizationInterceptor` (compiled against Spring Framework 7 servlet/security types) into a Spring Framework 6 runtime, which is exactly the kind of classpath mismatch `provided`/`optional` Maven scope does not protect against. **Recommendation: build on Spring Boot 4.1.x.** This is a correction to make in `PROJECT.md`/`ROADMAP.md`, not a footnote — flag it to the user before phase planning locks in "Spring Boot 3".

### Java: Spring Boot 4.1.x details

| Concern | Recommendation | Why |
|---|---|---|
| gRPC client | **Do not add a separate gRPC library.** The AXIAM Java SDK already bundles `grpc-netty-shaded`, `grpc-protobuf`, `grpc-stub` (all pinned to `1.84.0` in the SDK's own `pom.xml`) and exposes `CheckAccess`/token-validate calls as plain Java methods on `AxiamClient`. Adding `net.devh:grpc-client-spring-boot-starter` on top would be redundant and is a dead end anyway — it is stuck compiled against Spring Boot 3.2.4 with no Boot 4 release. | Spring Boot 4.1's own first-party Spring gRPC auto-configuration (server *and* client transports) landed 2026-06-10, but the Management Platform never serves or calls gRPC except through the SDK's own client, so there is nothing for it to configure here. Keep it in your back pocket only if a future phase needs the Management Platform to expose its own gRPC surface. |
| PostgreSQL access | **jOOQ 3.19+** over Spring Data JPA/Hibernate, and over plain Spring Data JDBC. | The 512 MB heap cap on the Pi is the deciding factor: Hibernate's first-level session cache, lazy-loading proxies and dirty-checking machinery are real, non-trivial heap residents for no benefit here — the domain (sites/buildings/apartments/devices/grants, mirrored into AXIAM's resource tree) needs precise, predictable SQL, not an object graph with lazy associations. jOOQ compiles to the exact SQL you write, with compile-time-checked, generated types from the Flyway-migrated schema, and no session/persistence-context overhead to size for. Spring Data JDBC is leaner still but pushes hand-written SQL into `@Query` strings with no generated-DSL safety net once you need the tree-walk joins (portfolio → site → building → apartment → device) this domain has throughout. |
| Migrations | **Flyway**, via `spring-boot-starter-flyway` (not bare `flyway-core`) + `flyway-database-postgresql`. | Spring Boot 4.x changed the auto-configuration contract: adding `flyway-core` alone no longer wires migrations at startup — the starter is required. This is a real "it silently does nothing" trap for anyone porting a Boot-3 mental model forward; call it out in the phase plan. |
| Heap / lean JVM settings for the Pi | `-XX:+UseSerialGC -XX:MaxRAMPercentage=50 -Xss512k -XX:TieredStopAtLevel=1 -XX:CICompilerCount=2` inside the container, with a hard container `mem_limit` (Compose `deploy.resources.limits.memory`) around 700–800 MB total (JVM heap ≈512 MB + metaspace/threads/native). Use `eclipse-temurin:21-jre-alpine` (or `-jre-jammy` if `musl` causes issues with the SDK's optional JNA/OPAQUE native binding) as the base image, both multi-arch. | `SerialGC` beats G1 (the Boot default) on a single vCPU-constrained container — G1's background threads and larger metadata overhead cost more than they save at this heap size. `TieredStopAtLevel=1` trims JIT memory/CPU on a machine that will never run this JVM long enough to benefit from C2. Skip GraalVM native-image: the SDK's optional OPAQUE support loads `libaxiam_opaque_ffi` via JNA at runtime (`dlopen`/`dlsym`), which native-image's closed-world analysis does not reason about — you'd need a reflection/JNI config exercise the SDK does not document, for a memory win CDS + tuned heap already captures most of. |
| Startup memory | Enable **AppCDS** (`-Xshare:dump` once, then `-XX:SharedArchiveFile=app-cds.jsa`) in the image build. | Cuts classloading memory/CPU at startup, which matters more on the Pi's slower cores than on the laptop; zero runtime behavior change. |

### Rust Device Twin details

| Concern | Recommendation | Why |
|---|---|---|
| MQTT client | **`rumqttc`** (current 0.24/0.25 line), not `paho-mqtt`. | `rumqttc` is pure Rust with a `rustls` TLS backend by default — exactly the TLS stack the AXIAM Rust SDK itself standardizes on (`reqwest = { features = ["rustls", ...] }`, explicitly *not* `native-tls`, per the SDK's own Cargo.toml comments). `paho-mqtt` is a Rust wrapper around the Eclipse Paho **C** library: it needs a C toolchain, OpenSSL dev headers, and `cmake` at build time, once per target architecture — the one thing you want to avoid when cross-building the Twin for `arm64` from an `amd64` buildx host. `rumqttc`'s pure-Rust `rustls` stack cross-compiles with nothing more than a Rust target added (`rustup target add aarch64-unknown-linux-musl` or a `cross`/`cargo-zigbuild` toolchain) — no second native dependency graph per architecture. |
| mTLS to the broker | `rumqttc::Transport::tls_with_config(...)` with `rustls::ClientConfig` built from the device/service PEM cert+key and the AXIAM root CA (loaded the same way the SDK's own `reqwest` client trusts a custom CA). | Matches the "every certificate anchored in the AXIAM organization CA" constraint without introducing a second crypto stack. |
| gRPC (`CheckAccess`) | Enable the AXIAM Rust SDK's own `grpc` feature (`tonic 0.14`, `tonic-prost`, `prost 0.14` — already the SDK's pinned versions) rather than adding an independent `tonic` dependency. | Same logic as Java: the SDK is the gRPC client, don't stand up a second one. |
| PostgreSQL access | **`sqlx` 0.8.6**, not `diesel`. | `diesel` is sync-first (needs `diesel-async` bolted on for an Actix/tokio app, a second dependency and a second mental model); `sqlx` is async-native and already the idiomatic Actix-web + Postgres pairing. Use features `runtime-tokio`, `tls-rustls-ring-native-roots` (again: rustls, and "native-roots" so the container's trust store — into which the AXIAM root CA is installed at provisioning time — is honored without a custom root-store plumbing exercise), `postgres`, `macros`, `migrate`. |
| Migrations | `sqlx::migrate!` embedded macro, own schema, own migration set — **not** Flyway. | The Postgres instance is shared but each service owns its schema end-to-end. Pulling the JVM-based Flyway CLI into the Rust build/release pipeline just to satisfy a "one migration tool" aesthetic costs more (a JVM install in the Rust CI/release image) than it buys; `sqlx migrate` needs nothing beyond the Rust toolchain already present. |
| SSE to the UIs | `actix-web-lab`'s `sse` module (`Sse::from_infallible_receiver(...).with_keep_alive(Duration::from_secs(15))`), version tracking `actix-web-lab` compatible with `actix-web 4.15.x`. | Hand-rolling `text/event-stream` streaming bodies over a raw channel works but reinvents keep-alive pings and the `data:`/`event:` framing `actix-web-lab` already gets right; it's maintained by the same team as `actix-web` itself, so it tracks actix-web releases closely. |

### C / C++ simulator MQTT clients

| Concern | Recommendation | Why |
|---|---|---|
| C (lights) | **`paho.mqtt.c`** (Eclipse Paho C client, current release line ≥1.3.16) | Available via **both** Conan (`paho-mqtt-c` on ConanCenter) and the vcpkg community port — the exact two package managers the AXIAM C SDK itself ships overlay ports/recipes for (`ports/axiam-c-sdk`, `conanfile.py`). Adopting the same two package managers for MQTT means one dependency-resolution story per simulator host, not two. |
| C++ (intercoms) | **`paho.mqtt.cpp`** (current release 1.6.0; vcpkg port `paho-mqttpp3` pinned slightly behind at 1.5.3 — pin to whatever vcpkg/Conan currently resolves rather than chasing GitHub's newest tag) | Ships an idiomatic C++ wrapper (`mqtt::async_client`, `mqtt::ssl_options`) that mirrors the AXIAM C++ SDK's own idiomatic style (`axiam::Client::builder()...`), and explicitly requires `paho.mqtt.c` ≥1.3.16 underneath — same underlying engine as the lights simulator, one less thing to reason about differently across the two hosts. |
| mTLS | `MQTTAsync_SSLOptions` (C) / `mqtt::ssl_options` (C++) with `keyStore`/`privateKey`/`trustStore` pointed at the simulator host's per-device cert/key and the exported AXIAM root CA — the exact same three files the SDKs' own libcurl-based REST device login already consumes. | Reuses one certificate set per virtual device across both the SDK's REST `auth/device` call and the raw MQTT connection; no second credential-provisioning path to build. |
| What NOT to use | `libmosquitto` (Eclipse Mosquitto's client library). | Not because it's a bad MQTT client — because it fragments the toolchain story for no gain: neither the C nor the C++ AXIAM SDK's build system (CMake + Conan + vcpkg overlay ports) has any precedent using it, its C++ bindings are third-party/unofficial (Paho ships an official one), and running two different MQTT client families across the two simulator hosts (C via Paho, C++ via Mosquitto, say) buys nothing while doubling the "how does mTLS get configured here" documentation. |

### RabbitMQ MQTT: authentication and authorization decision

This is the "decided in phase research" item the roadmap is waiting on. The recommendation is unambiguous:

**Authenticate devices to the MQTT listener via mTLS (`ssl_cert_login = true`), and authorize per-topic access with a small custom `rabbitmq_auth_backend_http` service built into the Device Twin. Do not use `rabbitmq_auth_backend_oauth2`.**

| Why not `rabbitmq_auth_backend_oauth2` | Evidence |
|---|---|
| The OAuth2 backend requires the presented JWT's `scope` claim to be pre-shaped as RabbitMQ permission grammar, e.g. `"read:vhost/topic"` or `"my_id.configure:*/*"` — a format AXIAM's tokens do not, and are not designed to, produce. | Read directly from `crates/axiam-auth/src/token.rs`: `AccessTokenClaims.scope` is documented as "OAuth2 scopes (space-separated string). Present when non-empty scopes are granted — both Client Credentials and Authorization Code flows." It is an application-defined OAuth2 scope string, not a RabbitMQ-shaped one, and it is **not populated at all** for the mTLS device-login path (`POST /api/v1/auth/device`) the architecture already commits to for devices — confirmed against `AccessTokenClaims`' doc comments and the "mTLS: … device mTLS login works over REST" note already in `PROJECT.md`'s AXIAM-capabilities section. |
| Devices don't hold a bearer JWT to present as an MQTT password in the first place — the whole point of the architecture (mTLS device certs from the AXIAM PKI, "Private keys never leave the simulator host") is that identity is proven by TLS client certificate, not by a token in the CONNECT packet. Bolting an OAuth2-shaped JWT onto MQTT auth on top of the mTLS handshake AXIAM already provides is solving an already-solved problem twice. | `PROJECT.md`'s architecture section and Key Decisions table ("Device ↔ Twin over MQTT on AXIAM's RabbitMQ … TLS with client certs"). |
| Making the OAuth2 backend work at all would require re-shaping AXIAM's own OAuth2 client/scope configuration to emit RabbitMQ-grammar scopes — which is exactly the "extending AXIAM" the project's Out-of-Scope list forbids. | `PROJECT.md` Out of Scope: "Extending AXIAM or its SDKs. Gaps are logged, not fixed." |

Concretely: set `{rabbitmq_mqtt, [{ssl_cert_login, true}]}` (RabbitMQ picks the username from the client cert's DN, or a specific SAN index via `mqtt.ssl_cert_login_san_index`) so each device's identity is exactly the identity already proven by its AXIAM-PKI-issued cert. Point `auth_backends` (for authorization only — cert login itself needs no backend round-trip) at `http`, and implement the four `rabbitmq_auth_backend_http` endpoints (`user_path`, `vhost_path`, `resource_path`, `topic_path`) as a tiny route inside the Device Twin's own Actix-web server — the Twin already owns the device registry and the MQTT bridge, so it already has everything needed to answer "may this cert-derived identity publish/subscribe on `domo/{tenant}/{device}/...`" without a second source of truth. This is a small piece of hand-rolled HTTP that talks to *our own* service, not to AXIAM — it does not count against the "use the SDKs for every AXIAM interaction" rule, but log it in the dogfooding findings anyway as "AXIAM has no native device-cert-to-MQTT-topic authorization primitive; we built our own."

### Caddy 2 (single-origin TLS reverse proxy, AXIAM-PKI certs, no ACME)

| Concern | Recommendation | Why |
|---|---|---|
| Version | 2.11.x (2.11.4, 2026-06-03) | Current stable; multi-arch official image (`caddy:2.11-alpine`). |
| TLS certificate source | **Static file certs**, not `tls internal` and not ACME. Caddyfile: `tls /etc/caddy/certs/caddy.crt /etc/caddy/certs/caddy.key` per site, with the cert/key issued by the AXIAM org CA during the bootstrap sequence described in `PROJECT.md`'s "TLS bootstrap implication." | `tls internal` mints certs from **Caddy's own** local CA — the opposite of "every certificate in the demo is issued by the AXIAM PKI." ACME (`acme_ca`, automatic HTTPS) needs a public CA and/or internet reachability for challenges — this is explicitly a local, LAN-only, no-internet-exposure demo. Global `auto_https off` plus explicit `tls <cert> <key>` per site is the correct, minimal Caddyfile shape. |
| Routing | Single Caddyfile, one `handle_path`/`reverse_proxy` block per prefix (`/staff`, `/resident`, `/api/mgmt`, `/api/twin`, `/axiam`) as already drawn in `PROJECT.md`'s architecture diagram. | Single origin avoids CORS and cookie-domain issues entirely — this is already the stated rationale in the Key Decisions table; Caddy just needs to implement it. |
| Client certs at the edge | Not needed. Browsers authenticate via OPAQUE (password never reaches Caddy); devices/services that use mTLS talk to AXIAM, the Management Platform, and RabbitMQ **directly**, not through the browser-facing Caddy instance. | Keeps Caddy's config to plain TLS termination + path routing — no `client_auth` block needed on the browser-facing listener. |
| Reloads on `just demo-reset` | Use Caddy's admin API (`POST /load`) or `caddy reload` after certs are re-issued, rather than a full container restart. | `demo-reset` re-issues every certificate; a graceful config/cert reload avoids a few seconds of downtime and matches how the AXIAM Pi-k3s guide already treats cert renewal (a reload, not a restart). |

### PostgreSQL version and Pi tuning

| Concern | Recommendation | Why |
|---|---|---|
| Version | **17.x** (`postgres:17-alpine`), not 18. | PostgreSQL 18 (GA 2025-09, currently at 18.6) is the newest major, but Spring Boot 4.x's Flyway starter has an open, reported issue against it: `spring-projects/spring-boot#49012`, "Spring Boot 4.0.2 fails at startup with Flyway: Unsupported Database: PostgreSQL 18.1." Given the Management Platform is already moving to Spring Boot 4.1.x (see the correction above), stacking an unresolved Flyway/PG18 compatibility bug on top of that is an avoidable risk for a demo with a hard deadline. PostgreSQL 17 has no such open issue and is fully supported by Flyway, jOOQ codegen, and `sqlx`'s compile-time macros today. |
| Image | `postgres:17-alpine` (official, multi-arch `amd64`+`arm64/v8`) | Alpine variant keeps the container small; official image needs no rebuild for arm64. |
| `shared_buffers` | 128–192 MB | The 25%-of-RAM rule of thumb assumes Postgres is the only tenant of that RAM; here it shares an 8 GB Pi with AXIAM's own SurrealDB+RabbitMQ+`axiam-server`, the JVM, and the Twin, inside a **4 GB total** budget. 128–192 MB is a "good enough for a two-schema, low-concurrency demo workload" number, not a tuned-for-throughput one. |
| `work_mem` | 4 MB | Kept low because `max_connections` × `work_mem` is the real risk under memory pressure, not single-query performance, at this data volume (114 devices, a few hundred rows across sites/buildings/apartments/devices/grants). |
| `max_connections` | 40 | Two application pools (Management Platform via HikariCP, Twin via `sqlx`'s pool) sized small (5–10 each) plus headroom for `psql`/tooling during the demo — no need for Postgres's default 100. |
| `effective_cache_size` | 512 MB–1 GB | Planner hint only (no allocation); set conservatively given the shared 4 GB budget rather than assuming the OS page cache has the Pi's whole 8 GB to itself. |
| Two schemas, one instance | Confirmed as the right call already in `PROJECT.md`'s Key Decisions ("mature Java and Rust drivers; lean enough for the Pi; avoids coupling to AXIAM's storage"). Each service (Java via Flyway, Rust via `sqlx migrate`) owns and migrates only its own schema. | Keeps migration ownership unambiguous without a second Postgres instance's fixed idle-memory cost. |

### Multi-arch image building

| Concern | Recommendation | Why |
|---|---|---|
| Builder | `docker buildx create --driver docker-container --use` on the amd64 laptop, plus `docker run --privileged --rm tonistiigi/binfmt --install all` once, to register QEMU for the arm64 target. | Standard 2026 buildx setup; the `docker-container` driver is required for multi-platform output (the default driver can't do it). |
| Java image | Build once per architecture with **no cross-compilation concerns at all** — Java bytecode is architecture-independent; only the base image (`eclipse-temurin:21-jre-alpine`, already multi-arch) needs to resolve per-platform. `docker buildx build --platform linux/amd64,linux/arm64 ...` just works without QEMU-emulated compilation. | The JVM is the one component in this stack where multi-arch is nearly free. |
| React portals | Build **once**, `linux/amd64` only, as a plain `node:22-alpine` build stage producing static files — there is no reason to build the frontend "for arm64" at all, since the output is architecture-independent JS/CSS. Copy the static output into whichever arch's Caddy image is being assembled. | Cuts the slowest part of a naive "build everything on both platforms" approach (Node/Vite builds under QEMU emulation are notably slow) entirely out of the arm64 path. |
| Rust Device Twin | **Cross-compile, don't emulate.** Use a `--platform=$BUILDPLATFORM` builder stage (native, fast) with `cargo` cross-compiling to `aarch64-unknown-linux-gnu` (via `cross` or a `zigbuild`-based image), then `COPY --from=builder` the arm64 binary into a `--platform=$TARGETPLATFORM` minimal runtime stage (e.g. `debian:bookworm-slim` or `gcr.io/distroless/cc-debian12`, mirroring exactly what AXIAM's own `docker/Dockerfile.server` already does with its `--platform=$BUILDPLATFORM ... AS wasm` stage). | This is the one component where naive QEMU-emulated `cargo build` for arm64 is genuinely slow (rustc under full-system emulation). AXIAM's own Dockerfile already demonstrates the pattern to copy (`FROM --platform=$BUILDPLATFORM rust:1.97-bookworm ... AS wasm`), so there is a working precedent in this exact codebase family to follow rather than invent. |
| C/C++ simulators | **Out of this concern entirely.** `PROJECT.md` fixes simulators to "Linux x86_64 only" — they are never built for arm64. | No multi-arch work needed for the simulator hosts at all. |

Recommend **vcpkg** if the team is already comfortable with CMake presets and wants a manifest (`vcpkg.json`) checked into the repo; recommend **Conan** if reproducible cross-compilation profiles for the arm64-vs-amd64 story matter more (irrelevant here since simulators are amd64-only) — given simulators never target arm64, this is a low-stakes pick; default to vcpkg for the simpler manifest-file workflow. |

## Alternatives Considered

| Recommended | Alternative | When to Use Alternative |
|-------------|-------------|--------------------------|
| Spring Boot 4.1.x | Spring Boot 3.5.x | Only if the AXIAM Java SDK later ships a Spring Boot 3-compatible optional-dependency line; as of `axiam-java-sdk` `1.0.0-beta16` it does not, so this is not a live option today. |
| jOOQ | Spring Data JPA/Hibernate | If the domain grows deep object graphs with genuine need for lazy loading/caching across many related entities — not the case here (a handful of small, shallow tables). |
| jOOQ | Spring Data JDBC | If the team wants the absolute smallest dependency footprint and is willing to hand-write every join as a `@Query` string without compile-time SQL checking. |
| `rumqttc` | `paho-mqtt` (Rust) | If the Twin ever needs an MQTT feature `rumqttc` lacks (e.g. certain enterprise broker extensions) — unlikely against RabbitMQ's plugin, which speaks standard MQTT 3.1.1/5.0. |
| `paho.mqtt.c` / `paho.mqtt.cpp` | `libmosquitto` | If a future non-AXIAM integration specifically requires Mosquitto's client (e.g. a Mosquitto-specific broker extension) — not the case against RabbitMQ. |
| `rabbitmq_auth_backend_http` (custom, in the Twin) | `rabbitmq_auth_backend_oauth2` | Only if AXIAM's OAuth2 client scopes are reconfigured to emit RabbitMQ-shaped scope strings **and** devices are switched to present a bearer JWT as their MQTT password instead of relying on the cert already required elsewhere — both changes are out of this project's scope. |
| TanStack Router + Query | React Router v7 (framework mode) | If the portals ever need SSR or a public, content-indexed surface — not the case for an internal staff console / resident app behind a LAN-only reverse proxy. |
| shadcn/ui + Tailwind | Mantine | If time pressure favors shipping generic, batteries-included admin components over bespoke device-tile visuals — a legitimate trade if the "polished, guided storyline" goal is deprioritized. |
| PostgreSQL 17 | PostgreSQL 18 | Once `spring-projects/spring-boot#49012` (Flyway/PG18 "Unsupported Database") is confirmed fixed in the Flyway/Boot4 versions actually pinned — re-check before committing long-term, this is a fast-moving compatibility gap, not a permanent one. |
| vcpkg | Conan | Either works against both C/C++ SDKs' overlay ports; pick based on team familiarity, not technical necessity (see Development Tools table). |

## What NOT to Use

| Avoid | Why | Use Instead |
|-------|-----|--------------|
| `net.devh:grpc-client-spring-boot-starter` (or any `grpc-spring`/`grpc-spring-boot-starter` fork) | Latest release (`3.1.0.RELEASE`) is compiled against Spring Boot 3.2.4 with no Spring Boot 4 path, and it would be redundant anyway — the AXIAM Java SDK already bundles and exposes gRPC `CheckAccess`. | The SDK's own `AxiamClient` gRPC methods; Spring Boot 4.1's first-party Spring gRPC auto-config only if a *non-AXIAM* gRPC need ever appears. |
| `rabbitmq_auth_backend_oauth2` | AXIAM's token `scope` claim isn't shaped for RabbitMQ's permission grammar, and devices authenticate via mTLS cert, not bearer JWT, per the architecture already committed to. Making it work would mean reconfiguring AXIAM's OAuth2 scope issuance — out of scope. | `ssl_cert_login` for authN + a custom `rabbitmq_auth_backend_http` endpoint (built into the Twin) for authZ. |
| Caddy `tls internal` for the browser-facing listener | Issues certs from Caddy's own local CA, contradicting the "every certificate is issued by the AXIAM organization CA" constraint. | Static `tls <cert> <key>` file directives, with certs minted by the AXIAM PKI bootstrap sequence. |
| Caddy ACME (automatic HTTPS / `acme_ca`) | Needs a public CA and/or internet-reachable challenge — this is a local, LAN-only, no-internet-exposure demo. | Same as above: static AXIAM-issued certs, `auto_https off`. |
| `libmosquitto` for the C/C++ simulators | No precedent in either AXIAM C/C++ SDK's build tooling (both ship Conan + vcpkg ports for Paho-style dependencies); its C++ bindings are unofficial. | `paho.mqtt.c` / `paho.mqtt.cpp`. |
| `paho-mqtt` (Rust wrapper around Paho C) for the Device Twin | Pulls in a C toolchain + OpenSSL per target architecture, which specifically fights the arm64 cross-build goal. | `rumqttc` (pure Rust, `rustls`). |
| `diesel` (sync core) for the Twin | Needs `diesel-async` bolted on to fit an Actix/tokio app; `sqlx` is async-native and already the standard Actix-web pairing. | `sqlx` 0.8.x. |
| Hibernate/Spring Data JPA for the Management Platform | Session cache + lazy-loading proxy overhead is a real cost against a 512 MB heap cap, for a shallow, well-understood schema that doesn't need an object graph. | jOOQ. |
| `flyway-core` alone (no starter) on Spring Boot 4.x | Silently does **not** auto-configure migrations under Boot 4's new auto-configuration contract — a "why didn't my migration run" trap. | `spring-boot-starter-flyway` + `flyway-database-postgresql`. |
| GraalVM native-image for the Management Platform | The SDK's optional OPAQUE support resolves `libaxiam_opaque_ffi` via JNA `dlopen`/`dlsym` at runtime — undocumented against native-image's closed-world reflection config, a real risk for a demo timeline. | Tuned JVM heap + AppCDS (see Java section). |
| PostgreSQL 18 (for now) | Open, unresolved Flyway/Spring Boot 4 compatibility issue (`spring-boot#49012`, "Unsupported Database: PostgreSQL 18.1"). | PostgreSQL 17.x. |
| Building the React portals per-architecture | Wasted build time: the output is arch-independent static assets. | Build once (`amd64` build host), serve from whichever Caddy image matches the deployment target. |

## Stack Patterns by Variant

**If a future phase needs the Management Platform to expose its own gRPC service (not just call AXIAM's):**
- Use Spring Boot 4.1's first-party Spring gRPC auto-configuration.
- Because it is now in-tree (no third-party starter dependency, no Boot-4-compatibility gap like `net.devh`'s).

**If the demo is ever asked to survive a broker restart with queued commands (currently out of scope — "no HA, no clustering" per PROJECT.md):**
- Reconsider MQTT QoS levels and RabbitMQ's classic-queue vs quorum-queue backing for the MQTT plugin's internal queues.
- Because the current recommendation (QoS as needed per message type, default plugin queue type) assumes the "local, LAN-only, no production hardening" scope holds; revisit if that constraint changes.
